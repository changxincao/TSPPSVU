# Experiment 1 与 2 代码—模型审计（2026-09-15）

## 审计结论

当前实现的主协议和数学模型映射基本正确，但尚不能直接启动正式 20-replication batch。已重新运行 7-carrier、4-lane、100-history、1-validation-origin 的端到端微型测试，Experiment 1 返回 8 种方法，Experiment 2 返回 RSAA、RCSAA、U/C-$\chi^2$、U/C-$W_1$、U/C-PCM 共 8 种方法，测试以 exit code 0 完成。该测试只证明接口、等式 recourse 和小算例求解链连通，不证明 20×60 正式实例的效果或效率。

## 当前两个实验实际求解的模型

Experiment 1 是 information/weighting selection。D 将 70/100 个训练需求压成一个逐 lane 算术均值场景；SAA-All 对全部历史场景等权；Tuned-SAA 在 $\{0.4,0.6,0.8,1\}$ 中选择最近历史比例；四种 kernel-CSAA 和 RF-CSAA 对同一需求点产生条件权重。八种方法都调用同一个 CPLEX 两阶段 SAA extensive form，只改变需求场景或概率，不改变采购模型。所有需求约束和 OOS recourse 均使用等式。

Experiment 2 固定 Experiment 1 由 validation 选出的 contextual family。RSAA/RCSAA 都求 exact mean--SD regularized model，区别仅是 RSAA 等权、RCSAA 使用条件权重；代码按 repair 或 compact 选用相应 exact LBBD/primal solver。U/C-$\chi^2$ 使用同一个 MOSEK conic modified-$\chi^2$ reformulation，只改变中心概率；U/C-$W_1$ 使用 box support、max-normalized average-$L_1$ ground metric 与 CPLEX exact CCG/oracle；U/C-PCM 使用相同的边际均值、边际方差和总需求方差结构，但分别由等权/条件权重计算经验矩，再由 RSOME/MOSEK 求 lifted-affine MISOCP。PCM 的 Optimal 只属于该策略近似，不是完全自适应两阶段 moment-DRO 的精确证书。所有最终 $y$ 都在相同的 1000 个 conditional OOS draws 上，用等式 recourse LP 重算真实成本。

## 正式运行前必须修正

1. `TRBSVUExperiment1Runner` 在 compact kernel 的 final test context 无正权重时，会按预定规则向上寻找有效带宽；但随后把这个只针对 final query 的 effective bandwidth 回写进 `selectedContextual`。Experiment 2 接收的是被 final query 改写后的值，并用它重新跑 30 个 validation origins。这违反“$C^\star$ 只由 Experiment 1 validation 冻结”的协议。应保留 validation-selected base $B^\star$ 传给 Experiment 2，final-query fallback 只作为每个 query 的局部 effective bandwidth。

2. `Solution.solveTimeSec` 在不同方法中不是统一的 end-to-end 时间：SAA只计 CPLEX `solve()`；$\chi^2$ 基本包含 Fusion 建模与求解；RCSAA/W1计各自外层算法；PCM只回传 MOSEK内部时间，排除了 Python/RSOME建模和进程开销。当前CSV的 `solve_time_sec` 不能直接形成公平Time列。应在 runner 的“权重已经给定、开始构造最终决策模型”到求解返回之间统一计 wall-clock，并把调参总时间另列。

3. W1当前 `timeLimitSeconds` 分别施加给每一次 master 和每一次 sample oracle，并不是整个 CCG 的总 wall-clock 上限。一次正式W1 solve可以远超3600秒，却仍表现为各子问题都没有超时。需要像RCSAA一样维护 remaining time，并将剩余时间传给master/oracle；否则运行时间和timeout比较不可信。

4. Validation solve 已强制要求 `certifiedOptimal`，PCM也只接受RSOME/MOSEK `Optimal`；但是Experiment 1和2的 final solve没有统一认证门控。若最终RCSAA/W1/其他模型有可行解但未认证，runner仍可能评价并写出OOS，或在没有 incumbent 时直接崩溃。正式performance表必须明确只接收认证解，或将timeout/gap作为独立状态并禁止混入已认证均值。

## 需要统一但不改变核心模型的问题

1. Experiment 1 CSV 给所有方法写入同一个 `context_family=C^\star`，会使D、SAA和未被选中的kernel行看起来像使用了所选family；同时 `selected_parameter` 写的是final fallback后的effective bandwidth，不是validation选出的原始 $B^\star$。应分别输出 `method_weight_family`、`validation_selected_B`、`final_effective_B`。

2. RCSAA/$\chi^2$入口都会先删除精确零权重场景；但只有 `DROModel` 的 modified-$\chi^2$ 路线会把小于 $10^{-8}$ 的正权重抬到 $10^{-8}$ 并重新归一化，exact RCSAA 不做正权重 floor。这个数值规则通常只改变至多约 $10^{-6}$ 的总概率质量，但它使 $\chi^2$ 模型的中心分布与 nominal CSAA/exact RCSAA 使用的原始权重不再严格相同，也没有写入现行说明书。正式比较前须保留并披露调整质量，或另行证明无需 floor；不能误写成 RCSAA 也修改了正权重。

3. Experiment 2自身CSV不重复selected nominal CSAA；该基准仍在同一replication的Experiment 1 CSV中。后处理必须按replication合并两表，不能把Experiment 2的8行误写成完整主表。当前也没有面向20个replications的正式聚合、配对区间和选择频率汇总器。

## 2026-09-15 修复与复核

补充核查compact kernel空支持：当前合成context四维均位于$[0,1]$，未额外标准化；$n=100,l=4$时实际带宽为$h_B=B/100^{1/8}\approx0.5623B$。对200个按当前生成器产生的独立replication检查final query，Epanechnikov和Triangular在$B=0.1$时200/200为空，在$B=0.5$时66/200为空，在$B=1,3$时均为0/200；最近历史context距离的min/median/max为0.0716/0.2491/0.5064。因此局部fallback确有实际必要，尤其不能假定$B=0.5$总能产生正权重。

### Kernel validation协议待用户冻结

不建议对每个$B$只平均“该$B$恰好有正权重”的validation origins，因为不同$B$将基于不同且选择性产生的子样本比较，小带宽可能只在最容易的query上被评价，验证成本会有乐观偏差。当前最干净口径仍是：30个origins中任一空支持则该$B$无效，所有候选在同一30个origins上比较。若最终query对所选$B^\star$空支持，可将同一kernel中“validation已在全部30个origins有效”的其余$B$按validation平均成本排序，选择final query上首个有效者；这比单纯选下一个数值更大$B$更符合训练内证据，且不读取OOS结果。另一种可选但含义不同的协议，是把“从base $B$逐级放大到首个有效$B$”定义成完整策略，并在全部30个origins上统一评价该策略，同时报告fallback率；不能简单丢弃空支持origin后求平均。

### Olist kernel保留z-score与training-max两种尺度

用户纠正“不应预先判定max有问题”。对任意两个context $x,x'$，z-score欧氏距离中的训练均值会相消，实际比较是$|x_k-x'_k|/\sigma_k$；training-max距离是$|x_k-x'_k|/m_k$。前者强调相对历史正常波动的异常程度，后者强调相对历史最大水平的比例。二者均是合法建模选择：z-score可能放大低方差或稀疏维度的少量跳变，max scaling也可能放大历史最大值很小的稀疏维度，并降低高峰值lane的相对贡献。因此不再把z-score描述为唯一正确方案。

代码以最小兼容方式保留两种选项：`StandardScaler.Mode.Z_SCORE`继续作为默认，确保既有Olist结果不改变；新增`TRAINING_MAX`，按训练窗口逐维最大绝对值缩放，全零维使用1避免除零。`Config.thetaScaling`控制核心`BatchRunner`，现有Config复制工具同步复制该字段。后续正式Olist比较必须在同一组training-only validation origins上对两种scaling做配对选择并输出`theta_scaling`，final OOS不得参与选择。本轮只完成实现和尺度性质自检，尚未运行Olist求解对照。

`instance.bin`不是额外随机数据，也不是Java对象序列化黑箱；它是项目自定义、有magic/version校验的无损二进制快照，逐项保存五类seed、$I/J/\alpha/\beta$、carrier/lane名称、spot、MQC、罚率、coverage、rate、capacity、final context、history和OOS。写文件采用`CREATE_NEW`防止同名重跑覆盖，加载时检查维数和尾随字节；同一算例随后从该文件重新读入求解，用于确保所有方法看到完全相同的冻结输入。CSV副本用于人工查看，binary用于精确复跑。
