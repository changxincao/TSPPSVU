# 2026-09-30 远程 Java 版本错配与 DRO 原生崩溃排查红线

## 1. 本次暴露的两类问题必须分开

### 1.1 Java class 版本错配

- 本机默认 `javac` 实际生成 Java 22 class（major version 66）。
- 远程正式运行环境是 Java 21，只接受 major version 65 及以下。
- 热更新 `TRBSVUForestWeights.class` 后，新的 worker 报
  `UnsupportedClassVersionError`；已经启动并加载旧类的 worker 不受影响。
- 该错误曾导致 CSAA-Exp 从后续 replication 起快速失败，也导致 RF-CSAA
  后续 replication 失败。它不是优化模型求解失败。

修复：使用 `javac --release 21` 重新编译；部署前检查 class 文件第 6--7
字节得到的 major version 必须为 65；本地与远程 SHA-256 必须一致。

永久规则：

1. 不得把本机默认 `javac` 生成的 class 直接复制到远程。
2. 优先在远程 JDK 21 下编译；必须本机编译时统一使用 `--release 21`。
3. 每次启动前扫描 staging 的全部 class；任何 major version 大于 65 时拒绝启动。
4. 热更新后只补跑缺少有效 `complete.txt` 的任务，不覆盖已经完成的结果。
5. 启动日志必须记录 Java 版本、class major、源码/二进制哈希。

`scripts/start_main_screen_25_remote.ps1` 已增加全量 class-major 启动门控。

### 1.2 DRO/JVM 原生访问违例

DRO 的 `EXCEPTION_ACCESS_VIOLATION` 与上述 class 版本错误不是一回事。
已有崩溃点分布在 MOSEK、CPLEX、JVM C2 编译器和无模块原生地址；MOSEK
11.0.25、11.0.30、11.2.5 均发生过。因此不能通过更换 MOSEK 补丁版本
宣称问题已经解决。

代码中发现 `try (Model M = ...)` 内再次调用 `M.dispose()` 的重复释放，已删除，
但修正后仍有原生崩溃，因此它不是唯一根因。正式重跑应使用 MOSEK 11.0.25，
限制在 P 核、先单进程验证，并优先把 MOSEK 求解决策与 CPLEX OOS 评价拆到
不同 JVM；OOS 评价还应避免为 1000 个样本反复新建 1000 个 CPLEX 模型。

## 3. 远程原生崩溃证据汇总

截至本轮排查，主实验 staging 中共找到 44 份 JVM 原生崩溃记录。崩溃并不
集中在一个固定 Java 方法或同一个求解阶段，而是分布在以下位置：

| 崩溃位置 | 已观察到的表现 | 解释边界 |
| --- | --- | --- |
| MOSEK native frame | 条件卡方模型求解过程中 JVM 直接退出 | 不是普通 Java exception；更换多个 MOSEK 11 补丁版本后仍出现 |
| CPLEX native frame | OOS 建模过程中在 `CPXnewcols`、`CPXaddrows` 等原生调用附近退出 | 说明问题不只发生在 MOSEK 主模型求解 |
| JVM C2 compiler / 无模块原生地址 | `hs_err_pid*.log` 指向 JIT 或无法归属的 native PC | 不能据此把根因唯一归到某一个求解器 |

远程机器在已检查的崩溃时刻仍有约 121 GB 可用内存，因此这些记录不符合
“内存耗尽导致 JVM 正常抛出 OOM”的特征；Windows 事件中也没有找到能直接
证明硬件故障的 WHEA 记录。另一方面，机器为 Intel Core i9-14900K，检查时
Dell BIOS 为 1.12.0、微码为 `0x12c`，而厂商已有更新的 BIOS。该信息只构成
运行环境风险线索，不构成 CPU/BIOS 已被证明有故障的结论。

检查时现存 Java 进程的 affinity 均为 `0xFFFFFFFF`，即没有被正式限制在
P 核。先前“固定 P 核后某一轮未立即崩溃”只能算短期现象，不能作为修复已
成立的证据。限制并发或 affinity 可以用于隔离问题，但不能替代完整复现。

此外，MOSEK 11.0.25、11.0.30 和 11.2.5 在远程均出现过原生崩溃。因此，
“升级或降级某一个 MOSEK 补丁版本即可解决”已经被现有证据否定。CPLEX
主版本为 22.1.1；本机与远程尚未逐文件核对 CPLEX/MOSEK DLL 的 SHA-256，
所以目前只能说产品主版本一致，不能说原生二进制逐字节完全相同。

## 4. 同一失败任务的本机完整复现

为区分模型/数据的确定性错误与远程环境问题，从远程复制了发生过崩溃的
`rep_001` 完整输入，以及对应的 TRI context choice，在本机执行同一个
Experiment 2 `C-Chi2` worker。复现口径如下：

- 采购实例：远程主筛选实验的 `rep_001`；
- context：TRI kernel，验证选择带宽 `B=0.9`；
- 参数网格：`lambda={0.1,0.25,0.5,1,2}`；
- 训练内验证：每个 lambda 使用 25 个 rolling validation origins；
- 最终评价：40 个 query，每个 query 继续执行 frozen final solve 和 OOS；
- 求解线程：4；单次时限 14,400 秒；
- 本机运行时：Java 22.0.1；class 用 `javac --release 21` 编译并确认 major
  version 65；
- 本机求解器：CPLEX 22.1.1，MOSEK 11。

完整运行结果为：

| 检查项 | 结果 |
| --- | ---: |
| validation solve | 5 x 25 = 125 次完成 |
| frozen final solve | 40 次完成 |
| `SOLVE_END` 总数 | 165 |
| 参数验证汇总 | 5/5 完成 |
| query 目录 | 40/40 完成 |
| `complete.txt` | 存在，`allRequestedMethodsCompleted=true` |
| Java/native exception | 0 |
| `hs_err_pid*.log` | 0 |
| worker exit code | 0 |

所有验证解和最终解均在当前默认 MIP gap 口径内通过实验层认证；本轮的目的
是复现原生崩溃，不把这些临时数值结果用于论文方法比较。核验完成后，本机
临时输入、编译产物、控制台日志和结果目录已全部删除；远程传输用临时 zip
也已删除，没有把诊断输出混入正式实验目录。

## 5. 当前可以下的结论与不能下的结论

本机对同一输入、同一方法和同一 4 线程配置完成 165 次求解，说明以下因素
不是“只要运行就必然崩溃”的充分条件：

1. `rep_001` 数据本身；
2. 当前 C-Chi2 数学模型及其固定参数网格；
3. MOSEK 求解与 CPLEX OOS 在同一个完整工作流中依次使用；
4. 单个 worker 使用 4 个求解线程。

因此，当前最符合证据的判断是：远程崩溃是远程 native runtime / JVM /
硬件与并发环境共同触发的不稳定，而不是已经定位出的确定性模型错误。
但是，一次本机成功仍不能证明某个具体组件无错，也不能把根因唯一归为
Java 21、CPU、BIOS、并发或某个 DLL。主要未控制差异包括：

- 本机为 Java 22，远程为 Java 21；
- 两台机器的 CPU、BIOS、微码和 Windows 运行环境不同；
- 尚未比较两边求解器 jar/DLL 的完整 SHA-256；
- 本机只完整复现了一个曾失败 replication，不是长期压力测试；
- 远程正式队列存在多进程并发，本机本轮只运行一个 worker。

## 6. 后续诊断优先级

如果远程再次出现同类原生崩溃，应按以下顺序处理，避免继续随机更换模型
参数或重复覆盖正式结果：

1. 保存新的 `hs_err_pid*.log`、worker stderr、Java/solver版本、任务名、
   replication/query/参数、进程线程数和退出码；
2. 对本机与远程实际加载的 CPLEX/MOSEK jar 和 DLL 计算 SHA-256；
3. 在远程用单 worker、4线程、固定输入复现，再与多 worker 情形配对；
4. 用同一 Java 主版本做本机/远程交叉测试，优先排除 Java 21 与 Java 22
   的运行时差异；
5. 若仍只在远程出现，更新 BIOS/微码后重复同一固定任务；
6. 如需进一步隔离，将 MOSEK 决策求解和 CPLEX OOS 评价拆为两个 JVM，
   通过持久化决策传递，判断崩溃是否与同 JVM 的原生库生命周期有关。

在完成上述配对之前，正式表格必须把 native-crash 任务标为失败并补跑，不能
把缺失任务当成同解、零收益或零运行时间；已经存在有效 `complete.txt` 的任务
不得因恢复队列而重复覆盖。
